title: Track checkouts and place files
description: Approve a checkout, choose links or copies, and keep a file local.

## Track a checkout

```sh
envden track /path/to/checkout
```

You can also pass a scan root to find several repos. Without a path, `track` starts in the current directory.

The scan never enters hidden folders like `~/.codex` or `~/.gradle`, dependency folders like `node_modules` or `Pods`, or the folders inside a checkout, where other clones are vendored code. Build output like `target`, `build` or `vendor` is skipped only inside a project, and tool folders like `~/Library`, `~/snap` or `~/go` only in your home folder. Worktrees and submodules of a checkout it finds are still listed, even when a worktree sits in a hidden folder such as `~/.t3/worktrees`. A scan root you name is always scanned, hidden or not.

Repos without a usable git remote are skipped and counted in one line. Add `--verbose` to `setup` or `track` to list each one.

### Env files you symlinked yourself

If a checkout's `.env` is your own link, say to `~/.config/dev-envs/app/.env`, envden asks once per target whether to manage it. On Yes, it copies that file's content into the store and replaces each link with its own. From then on the checkouts use the synced copy, and edits to the original file no longer reach them. envden never changes the original, and `envden untrack` puts your link back. Only regular files are offered, not named pipes like 1Password's local `.env`. A link to another env file in the same checkout, like `.env -> .env.development`, is left as is. If the target is missing, or a synced copy with different content already exists, envden leaves the link alone. On No, or without a terminal, the links stay and are counted in the summary.

Approve each checkout in your terminal before envden places files there. `--yes` on setup doesn't bypass this step. Approval is stored outside the checkout, and a changed remote doesn't silently change its repo identity.

A git worktree of an approved clone is approved on its first `pull`, `push` or `track` there, and envden prints `Approved worktree <path> (auto-approve-worktrees)`. This is on by default. Only worktrees registered in the clone's own `.git` count, since making one already needs write access to the clone. A separate clone, a checkout recreated at an approved path, or a worktree of an unapproved clone still asks. To ask for every worktree:

```sh
envden config auto-approve-worktrees off
```

Turning it back on needs your terminal. `envden untrack <path>` removes an approval.

## Link mode

By default, envden places a symlink into your device's store:

```text
~/.envden/store/<repo-id>/<path-in-repo>/<file>
```

Approved clones and worktrees of the same repo share that store file. In a monorepo, `apps/web/.env` keeps its path under the repo's store directory.

Repo identity comes from the `origin` remote, or the only remote if there is no `origin`. envden asks when the choice is ambiguous. Your global `url.<base>.insteadOf` rewrites apply, SSH host aliases are resolved, and ports are ignored, so SSH and HTTPS clones of one repo share files. The Repo ID is encrypted before upload.

Store directories use `0700` permissions and files use `0600`. Before placement, envden checks git's ignore rules and adds a missing exclusion to the checkout's git exclude file. It refuses tracked files.

## Copy mode

Choose copies when a tool or container needs a regular file:

```sh
envden track /path/to/checkout --copy
```

Each copy has its own sync base. Edits in one checkout don't immediately change another checkout's file.

If symlinks aren't available, envden asks for consent before placing copies. It also offers copy mode once per checkout when the root contains `.devcontainer/`, `docker-compose*.yml` or `Dockerfile`.

Save a placement preference for a checkout:

```sh
envden config placement /path/to/checkout copy
envden config placement /path/to/checkout link
```

This saves the preference; it doesn't immediately convert existing files. Placement uses the choice when you track the checkout.

## Keep a file local

For a per-worktree setting such as `PORT`, mark the managed file local-only before editing it:

```sh
envden local-only /path/to/checkout/.env
```

It becomes a regular copy in that checkout. envden skips it during push and pull and suppresses sync notices for it. Other checkouts keep syncing their versions.

## Stop tracking a checkout

```sh
envden untrack /path/to/checkout
```

This removes the checkout's approval and tracking records and restores regular files in place of managed links. A file envden took over from your own link gets that link back. It doesn't delete the vault's files or untrack other checkouts.

## Recover a replaced link

An atomic editor save, `sed -i` or `cp .env.example .env` can replace a symlink with a regular file. envden relinks a file that matches the store or an older synced version.

If it differs, envden marks the checkout detached, keeps both versions and asks you what to do on the next interactive command. The shell notice doesn't repair files.

## Share files with a fork

When an `upstream` remote already has env files, envden offers to alias the fork so it shares them. It asks once, and only if no checkout of the fork already has placed files.

If a checkout's remote changes, for example after a repo is renamed, run `envden untrack <path>` and then `envden track` to approve it under its new Repo ID.

## Use env files in Docker builds

Exclude env files from the build context:

```text title=".dockerignore"
.env
.env.*
!.env.example
```

Pass the file to the build as a BuildKit secret:

```dockerfile title="Dockerfile"
# syntax=docker/dockerfile:1
FROM node:22
WORKDIR /app
COPY . .
RUN --mount=type=secret,id=dotenv,target=/app/.env npm run build
```

```sh
docker build --secret id=dotenv,src=.env .
```

The mount exists for that `RUN` step. Copy mode isn't a build secret mechanism; a copied file included in the build context can land in an image layer. Your build command must also avoid embedding secret values in its output.
