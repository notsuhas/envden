---
title: Placement modes
description: How env files from the store appear in a checkout, as links or as copies.
---

## The store

Each device keeps the real env files in a store in your home folder:

```text
~/.envden/store/<repo-id>/<path-in-repo>/<file>
```

Folders are `0700` and files are `0600` (ACLs on Windows). In a monorepo, `apps/web/.env` maps to `<repo-id>/apps/web/.env`.

Placement is how a store file appears in a checkout.

## Repo ID

A repo's identity comes from its remote, as `host/path`. envden reads `git remote get-url origin`, falls back to the only remote, and otherwise asks. Every checkout with the same Repo ID shares env files.

The Repo ID is never sent to the server in the clear.

## Link mode

The default. The env file in a checkout is a symlink into the store, so every clone and worktree of a repo reads the same file.

Before linking, envden checks that git ignores the path. If it doesn't, envden adds the path to the checkout's exclude file.

## Copy mode

The env file is a real copy. Each copy tracks the last version it agreed with the server, and push detects changes against that.

envden never switches to copy mode on its own:

- When symlinks aren't available, it explains why and asks before placing copies.
- When a checkout's root contains `.devcontainer/`, a `docker-compose*.yml` file or a `Dockerfile`, it offers copy mode once, in an interactive terminal.
- `envden track --copy` chooses it for the checkouts it tracks.
- `envden config placement <path> link|copy` saves the choice for one checkout.

## Local only

You can mark a file in one checkout as deliberately different, for example a per-worktree `PORT`. It becomes a copy that is never pushed or pulled, and envden doesn't nag about it.

## Detached checkouts

Some tools replace a link with a regular file: an atomic save, `sed -i`, or `cp .env.example .env`.

- If the new file matches the store, or an older synced version, envden relinks it.
- Otherwise the checkout is marked detached. envden keeps both versions and asks you on the next interactive command.

This is never silent, and the shell line never does it.

## Approved checkouts

A checkout receives env files only after you approve it once, in the terminal. `--yes` doesn't skip the question.

- A worktree of an approved repo gets a shorter question, but is never approved automatically.
- A changed remote never silently remaps an approved checkout.

## Forks and moved repos

When a checkout has an `upstream` remote whose Repo ID already has env files, envden asks once whether to share them. `envden alias` does the same by hand, and also fixes a renamed or moved repo.

## Docker builds

A build doesn't need env files in its context. Keep them out with `.dockerignore`:

```text title=".dockerignore"
.env
.env.*
!.env.example
```

Give a build step the file with a BuildKit secret mount. The file is mounted for that one `RUN` step and never lands in an image layer:

```dockerfile title="Dockerfile"
# syntax=docker/dockerfile:1
FROM node:22
WORKDIR /app
COPY . .
RUN --mount=type=secret,id=dotenv,target=/app/.env npm run build
```

```sh
docker build --secret id=dotenv,src=.env .
```

Copy mode is not recommended for builds, because a real file in the build context can end up in an image layer.

## Windows

Setup tries to create a symlink. If that fails (no Developer Mode, or it's locked by an admin), it explains why and asks before using copy mode.
