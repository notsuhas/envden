---
title: Security
description: How envden protects files, verifies history and limits checkout access.
---

## Files are encrypted on your devices

Your device encrypts files with XChaCha20-Poly1305 before upload. File names and Repo IDs are encrypted too. Files are padded in 256-byte steps to reduce size precision.

Each file's encryption binds it to the vault, encryption epoch, file ID and version. A signed manifest binds the ciphertext hashes. Devices verify the manifest and the signed device-membership history before accepting changes.

A device remembers the last history checkpoint it accepted. It rejects rollback and stops when it encounters a conflicting branch. The server can't add a device on its own. Tailscale carries traffic, but envden doesn't use Tailscale identity headers to authorize requests.

## Checkouts need your approval

A folder doesn't receive secrets just because its git remote matches a repo. You approve each clone in your terminal. Approval lives outside the checkout, and `--yes` doesn't bypass it.

A worktree registered in an approved clone's own `.git` is approved without asking, since creating one already needs write access to that clone. Separate clones, recreated checkouts and worktrees of unapproved clones still ask. `envden config auto-approve-worktrees off` turns this off; turning it back on needs a terminal.

Pulled paths are checked for traversal and symlinks escaping the checkout. Placement uses directory handles on macOS and Linux when FFI is available.

## Protect your recovery code

The recovery code is 128 random bits. It seals the recovery envelope on the server and proves to the server that you hold it; the server keeps only a public key derived from it. No device stores the code, so keep it in your password manager. With it, anyone can open the vault, so treat it like that password manager's own master key. If it may have leaked, replace it from a device: see [Manage the vault](/docs/vault).

## New devices are approved by comparing words

A new device joins only when a device already in the vault approves it and both screens show the same three words. The new device commits to its keys before the approving device picks its random value, so neither the server nor another device on your network can choose words to match yours. Each attempt is one guess, right about once in eight billion tries, and you see every wrong guess as mismatched words. Both screens ask, because each protects a side: the approving screen keeps strangers out of your vault, and the new screen keeps the new device from joining a vault someone else made.

Local store files use `0600` permissions and directories use `0700`.

## Where device keys are kept

Device keys are private files in `~/.envden/state/keys`, like SSH keys in `~/.ssh`. Each file is `0600` in a `0700` folder, so only your user can read them. `envden doctor` fails if that changes.

envden doesn't use the OS keychain. Your synced env files are plaintext on disk already, and any program running as you could ask the keychain for the keys by running envden. A keychain would add prompts after every update without adding protection. Full-disk encryption protects the key files the same way it protects your env files.

## What envden can't protect against

- A compromised member device can read the files and keys it has access to. Removing it doesn't erase downloaded files or prevent decryption of older ciphertext with keys it kept. Rotate exposed credentials after removal.
- A lost or stolen device keeps syncing until another device removes it with `envden device rm`. Files already on disk depend on your OS login and disk encryption.
- The server can deny service or show devices separate branches of history. A device stops when it sees the other branch. A server colluding with a removed device or an old recovery key can fork history.
- Encryption doesn't hide rough file sizes, timing, device count or device names from the server.
- Answering yes to words you didn't compare defeats the check. Only approve a device you're adding yourself.
- When FFI is unavailable, a local process can race a parent-directory replacement after the final path check.

## Cryptographic implementation

The protocol uses pinned versions of `@noble/ciphers`, `@noble/curves`, `@noble/hashes` and `@hpke/*`, and the BIP-39 English wordlist. envden's protocol combines these primitives; its encodings and test vectors are in [PROTOCOL.md](https://github.com/notsuhas/envden/blob/main/docs/PROTOCOL.md).

The [threat model](https://github.com/notsuhas/envden/blob/main/docs/DESIGN.md#threat-model) describes the trust assumptions behind these protections.
